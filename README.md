# neb-x

NebulaX Hackathon submission for **Problem Statement 3 — Train Condition Monitoring**.

Problem statement source:
[aochinwen/NebulaX-Hackathon-ProblemStatement](https://github.com/aochinwen/NebulaX-Hackathon-ProblemStatement) (`PS3/`)

## The problem

Detect faults and estimate degradation from raw rail-vehicle sensor time series across four
independent subsystems, each worth 25% of the Overall Score.

| Subsystem | Task | Metric | State |
|---|---|---|---|
| Door | Find each door open/close cycle in a continuous stream and classify it `Normal` vs `Abnormal resistance` | IoU-weighted F1 | **implemented** |
| ACV | Rank the cars in a train from most- to least-likely to have a refrigerant leak | Linear rank-decay | **implemented** |
| Rail Corrugation | Classify `Normal` / `Side I` / `Side II` from axle-box vibration | Macro F1 | not started |
| SHM | Estimate cumulative fatigue damage from dynamic stress data | `max(0, 1 − MAPE)` | not started |

Each subsystem's authoritative definition — schema, labels, exact scoring formula with a worked
example — is its info kit under [docs/](docs/). The table above is a convenience summary and loses
to the info kit wherever they disagree.

## Deliverables

1. A demo video (≤3 min) of the app in use end to end.
2. `predictions.zip` — one `*_predictions.csv` per subsystem attempted, flat at the top level.
3. An app that lets a non-technical user upload a data file and get a prediction back. The
   submitted predictions must be generated by running the held-out test files through it.

## Setup

```bash
git clone https://github.com/nebulax-group/neb-x.git && cd neb-x
uv venv                                   # creates .venv
uv pip install -r requirements.txt
```

**Use `uv`, not `pip`.** The virtualenv is uv-managed and has no `pip` inside it, so
`pip install -r requirements.txt` fails with a confusing error. To add a package later:
`uv pip install <name> --python .venv/Scripts/python.exe`.

The datasets are not in git (~6 GB). Clone the organisers' repo and copy `PS3/02_Datasets/` into
`data/` following the mapping in [data/README.md](data/README.md), then check the machine:

```bash
.venv/Scripts/python.exe scripts/check_env.py     # Windows
.venv/bin/python scripts/check_env.py             # macOS / Linux
```

Every command below uses the Windows interpreter path; substitute `.venv/bin/python` elsewhere.

## Running the two implemented subsystems

**Tests** — 48 of them, covering both subsystems end to end:

```bash
.venv/Scripts/python.exe -m pytest tests/ -v
```

The ACV tests read every case workbook through openpyxl and take about four minutes. That is
expected, not a hang.

**Door** — train, then predict:

```bash
.venv/Scripts/python.exe -m src.door.train
# -> Door CV accuracy 1.0000 +/- 0.0000 over 110 cycles (0 errors)
# -> checkpoint written to outputs/models/door/classifier.joblib

.venv/Scripts/python.exe -c "from src.common import config; from src.door import predict; \
config.PREDICTIONS_DIR.mkdir(parents=True, exist_ok=True); \
f = predict.predict([config.TEST_PATHS['door']]); \
f.to_csv(config.PREDICTION_PATHS['door'], index=False); print(f['prediction'].value_counts())"
# -> 30 Normal, 8 Abnormal resistance, across 38 rows
```

**ACV** — no training step; the method fits no parameters:

```bash
.venv/Scripts/python.exe -c "from src.common import config; from src.acv import dataset, predict; \
config.PREDICTIONS_DIR.mkdir(parents=True, exist_ok=True); \
f = predict.predict(dataset.test_case_paths()); \
f.to_csv(config.PREDICTION_PATHS['acv'], index=False); print(f.to_string(index=False))"
# -> acv_test_case.xlsx,01|03|07|04|08|06|02|05
```

**ACV confirmation report** — read this before trusting the ranking:

```bash
.venv/Scripts/python.exe -c "from src.acv import dataset, report; \
print(report.confirmation(dataset.test_case_paths()[0]).to_string(index=False))"
```

## How the two implemented subsystems work

**Door.** The controller only samples while a door is moving, so cycle boundaries are silences in
the stream: inside a cycle rows are 20 ms apart, between cycles the recorder goes quiet for 10 s or
more. Splitting on that gap reproduces all 110 labelled cycles exactly — same start, same end, same
row count — which makes every IoU in the official metric 1.0 and collapses the score to plain
accuracy on the labels.

Classification uses one feature: a cycle's mean motor current divided by the median of its own
operation **within its own recording**. Absolute milliamps do not transfer between doors, and the
info kit says so in §1.2.2; a cycle's excess over its own door's typical cycle does. Scaling all
currents by 0.85×–1.20× costs a raw threshold up to 80 of 110 cycles and costs this feature nothing.

**ACV.** Each car reports its cabin temperature and its cooling setpoint. Subtract, average over the
file, rank descending. A healthy car sits at or below its target; a leaking car runs above its own
target because it cannot keep up. That single signal ranks the true faulty car first in all five
cases sharing the held-out file's schema.

Full reasoning, the measurements behind every choice, and the ideas that were tried and rejected:
[docs/superpowers/specs/2026-09-18-door-acv-design.md](docs/superpowers/specs/2026-09-18-door-acv-design.md).

## Three things that silently score zero

Learned the expensive way; all three are guarded by tests.

1. **Rebuilt or reformatted identifiers.** `file_id` must be the source filename verbatim. Door's
   timestamps are not zero-padded (`2023-7-5-0-0-3-700`), so a round trip through any formatter
   emits `2023-07-05…` and matches nothing.
2. **Car ids read as numbers.** `pd.read_csv` without `dtype=str` turns `01` into `1`, and the ACV
   submission says `1|3|7` instead of `01|03|07`.
3. **A car missing from `ranked_cars`.** The organisers score an omitted car as zero, so a car whose
   signal is unusable is ranked last, never dropped.
